# 当前遥测与实时图传的负载预算

核对日期：2026-09-09。依据当前 `code/vofa.c`、`code/vofa_task.inc`、`code/vision_core.c` 和无线串口配置；下述吞吐量是计算值，不是实车性能测量。

## 数值遥测

UART2 为 115200、8N1，每个数据字节占 10 位，因此单方向理论有效载荷上限为 **11520 B/s**。无线实际吞吐还取决于模块空口、RTS、干扰和重传。

当前正常上报目标频率：Run 25 字段 / 50 Hz；stat 15 字段 / 10 Hz；握手后辅助 att 3 字段 / 10 Hz；task 13 字段 / 5 Hz。taskevt 随状态变化发送，出队上限 50 条/秒。Schema 读取和参数应答还会消耗额外带宽。

按车端真实格式字符串生成三组示例 Run 帧，再假设状态、辅助姿态、任务等合计 1200 B/s：

| 示例 | Run 字节/帧 | Run 加辅助数据 | 理论串口占用 |
| --- | ---: | ---: | ---: |
| 小数值 / 多数为零 | 122 | 7300 B/s | 63% |
| 一组代表性运动数值 | 144 | 8400 B/s | 73% |
| 较多负号及较大数值 | 177 | 10050 B/s | 87% |

这些是示例预算，不能当作最坏情况上界。实际值位数、运行时长、事件突发、Schema 读回都会改变负荷。可在上位机看稳定运行期间 RX B/s、遥测缺口和 MCU TX 丢弃计数，结合空口条件判断余量。

车端串口收发没有整帧阻塞等待：1 ms 中断最多搬入 32 B，向空闲硬件 FIFO 搬出最多 16 B；RTS 阻塞时直接返回。格式化在 CPU0 主循环，发送环为 2048 B，Run 和 task 入队为应答等预留空间，拥堵时丢遥测帧。该设计限制了中断内收数工作量，但浮点转字符串、快照、短临界区和总线访问仍有开销。

不能从源码直接断言 CPU 占用为某个百分比，也不能据 PC Mock 测试保证车端无影响。需要测量控制中断最长耗时、周期抖动、CPU1 视觉帧间隔、发送队列丢弃，以及遥测开关前后的差异。

若保持当前无线硬件，优先考虑让 Run 遥测从 50 Hz 降到 25 Hz（不改变 1 ms 控制周期），或把 ASCII 多字段改成有版本、校验和的二进制帧，并限制运行时全量 Schema 读取。这些属于后续车端通信改造建议，本次未执行。

## 摄像头数据量

188×120、8 位灰度每帧为 **22560 B**；二值图只有逐位打包成 1 bit/像素后才降为 **2820 B**。当前程序的二值图缓冲仍按字节存储，不能直接认为已经压缩到八分之一。

| 帧率 | 灰度有效载荷 | 灰度净数据带宽 | 位打包二值图 |
| --- | ---: | ---: | ---: |
| 1 fps | 22.56 KB/s | 0.18048 Mbps | 2.82 KB/s |
| 5 fps | 112.8 KB/s | 0.9024 Mbps | 14.1 KB/s |
| 10 fps | 225.6 KB/s | 1.8048 Mbps | 28.2 KB/s |
| 20 fps | 451.2 KB/s | 3.6096 Mbps | 56.4 KB/s |

KB 按 1000 B；尚未加帧头、分包、校验、链路编码和重传。原串口独占传一张灰度图至少约 1.96 秒，位打包二值图至少约 0.245 秒；叠加现有数值遥测后会更慢。直接在这条链路上加连续原图不合适。

## 可行方向

1. **小改动先看视觉结果**：传低频边线、中线、有效标志或少量采样点，上位机重建简图。需要控制点数和频率；这不是原始摄像头图像。
2. **完整图像走独立高速链路**：TC264 输出有界的图像快照，通过 SPI 连接 Wi-Fi 模块，再由模块送到 PC。先以 188×120 灰度 5～10 fps 验证，图像有效载荷约 0.9～1.8 Mbps，还需留链路余量。仓库自带 Wi-Fi SPI 驱动可作为起点，但当前未接入，模块、引脚、电源、吞吐和等待方式必须核对。
3. **保护现有控制/视觉任务**：CPU1 只在处理完成后发布快照，独立缓冲避免阻塞下一帧采集；不在 1 ms 控制中断内压缩或等待 Wi-Fi。图像发送有预算、可超时丢帧、不排长队，断网时也不能阻塞控制或正常视觉发布。

当前屏幕快照有 request/read/release 所有权，不能让网络和车载屏幕同时无协调占用同一快照。DMA、双缓冲和 Wi-Fi 的实际 CPU/总线负担仍需测量。也不应为降低网络带宽，未经评估就在控制核心加入 JPEG 压缩。

ESP32 一类模块支持通过 SPI / SDIO / UART 等接口为主控提供 Wi-Fi，架构上可做通信卸载；这并不保证任意模块或现有驱动都达到目标吞吐。参考 [Espressif 官方规格](https://www.espressif.com/en/products/socs/esp32/specifications)。
